# 筋トレ管理アプリ

種目・重量・回数・セット数・日別体重を記録できる筋トレ管理アプリです。
自分のトレーニングに合わせた種目の登録や、部位・細かい分類による記録の管理ができます。

V2ではSupabaseによる認証とデータベース保存を導入しました。
同じアカウントでログインすることで、スマホ・PCから自分の記録を利用できます。

## 公開URL

https://mikiya-web.github.io/workout-app/

利用にはアカウント登録とログインが必要です。

## 制作背景

普段の筋トレで使っていた記録アプリでは、新しい種目の登録や、同じ部位の中でさらに細かく分類することができず、不便に感じていました。

そこで、自分が行う種目を自由に登録し、部位だけでなく細かい分類でも記録を整理できるアプリを制作しました。

V1ではブラウザ内にデータを保存する形で公開しました。
V2では、ジムではスマホ、自宅ではPCという使い方ができるように、ユーザーごとにデータを保存する構成へ変更しました。

## 主な機能

### アカウント管理

- メールアドレスとパスワードによる新規登録・ログイン
- 確認メールによるメールアドレスの確認
- ログアウト
- メールによるパスワード再設定
- ユーザーごとの初期種目・分類の作成

### 種目・分類の管理

- 種目の追加・編集・削除
- 部位と任意の細かい分類の設定
- 分類の追加
- 種目名・部位による検索と絞り込み
- 記録に使われている種目の削除防止

### トレーニング記録

- 記録の追加・編集・削除
- 複数セットの重量・回数の入力
- メモの入力
- 同じ日付・種目の重複記録の防止
- 日別体重の登録・更新
- トレーニング記録を追加せず、体重だけを保存
- 種目名・部位・分類・日付による検索と絞り込み
- 日付の新しい順での記録表示
- 通常種目・自重種目のボリューム計算

### データ保存・通信への対応

- Supabaseのデータベースへの保存
- 同じアカウントでのスマホ・PC間のデータ共有
- データ取得結果の型・整合性チェック
- 保存中の連続操作の防止
- 通信失敗時のエラー表示と入力内容の保持
- 再送時の重複保存対策
- 更新番号による編集・削除の競合検出

## 使い方

1. 新規登録し、確認メールのリンクからメールアドレスを確認します。
2. ログイン後、「種目管理」で使用する種目を確認・追加します。
3. 記録の入力画面で、日付・種目・重量・回数などを入力して保存します。
4. 「記録一覧」で、過去の記録を確認・検索します。

新しいアカウントには、初期種目7件・分類13件が用意されます。
トレーニング記録は空の状態から始まります。

懸垂など、体重を含めてボリュームを計算する種目では、その日の体重も入力してください。
自重だけで行う場合は、追加重量に0kgを入力します。

別の端末で保存した変更を表示するには、画面を再読み込みしてください。

### 確認メール・パスワード再設定について

確認メールやパスワード再設定メールのリンクは、送信操作をした端末の同じブラウザで開いてください。

メールが届かない場合は、迷惑メールフォルダや受信拒否設定を確認してください。
キャリアメールでは、送信元アドレスの受信許可が必要になる場合があります。

## 工夫した点

### 自分のトレーニングに合わせた種目・分類の管理

種目を自由に登録できるようにし、部位に加えて任意の細かい分類を設定できるようにしました。

分類は部位と紐付け、選択した部位に合う分類を選べるようにしています。
DB側でも、種目と分類の持ち主・部位が一致することを外部キーで確認しています。

### 自重種目に対応したボリューム計算

通常の種目は、各セットの「重量 × 回数」を合計します。

懸垂などの自重種目は、各セットの「（その日の体重 ＋ 追加重量）× 回数」を合計します。

体重を計算に含めるかどうかは、種目だけでなく記録にも保持しています。
同じ種目の設定を後から変更しても、過去の記録の計算方法を維持します。

日別体重は、その日の記録で共有します。
体重を変更すると、その日の自重記録のボリュームも再計算されます。

### ユーザーごとのアクセス制限

各データにユーザーIDを持たせ、RLSによってログイン中の本人のデータだけを読み取れるようにしています。

アプリからテーブルへ直接追加・更新・削除する権限は与えず、DB関数をRPC経由で呼び出します。
各関数でログイン状態とデータの持ち主を確認してから処理します。

画面でも、アカウントが切り替わったときにユーザー用のコンポーネントを作り直し、前のアカウントのデータや入力状態を引き継がない構成にしています。

### 記録・セット・体重をまとめて保存

トレーニング記録・所属するセット・日別体重を、1回のDB処理でまとめて保存します。

途中で入力の不整合や更新競合が見つかった場合は、処理全体を取り消し、一部のデータだけが保存される状態を防ぎます。

また、記録を削除すると所属するセットも削除されますが、日別体重は残ります。

### 更新競合と重複保存への対策

データに更新番号（revision）を持たせ、編集開始時の番号とDBの番号を比較しています。

別の画面で更新されていた場合は、古い内容でそのまま上書きせず、エラーを表示します。
削除時にも更新番号を確認します。

新規保存では、同じ入力内容の再試行に同じUUIDを使用します。
DB側でも保存済みの内容を比較し、通信の応答を受け取れず再送した場合の重複登録を防ぐ仕組みを設けています。

### 画面の分割と状態の管理

記録一覧・記録入力・種目管理の3画面に分けています。

記録や体重の取得・保存、フォームの状態管理をカスタムフックの`useWorkoutRecords`に分離しました。
画面を切り替えても入力内容を保持し、フォームや一覧の表示はコンポーネントに分割しています。

通信中は関連する操作を制限します。
保存に失敗した場合は入力内容を残し、正常な保存結果を確認してから一覧へ反映します。

### フロントエンドとDBの両方でデータを検証

入力画面では、日付・重量・回数・必須項目などを検証します。

DB側でも、外部キー・一意制約・CHECK制約・関数内の検証を使い、データの整合性を保ちます。

DBから取得した値は、そのまま型を決めつけず、必要な項目・数値の範囲・所有者・セットの並び順などを確認してから画面で使用します。

### 公開処理の自動化

GitHub Actionsで依存関係のインストール・lint・buildを実行し、GitHub Pagesへ公開しています。

公開ビルドでは、Supabase URLとPublishable KeyをGitHub Actions Secretsから渡しています。
これらはブラウザで使う接続情報であり、公開用JavaScriptに含まれます。データの保護はRLSとDB側の権限・所有者確認で行います。

## データ保存と現在の制限

- V2のトレーニングデータはSupabaseに保存します。
- 同じアカウントでログインすると、別の端末・ブラウザでも利用できます。
- 他の端末で行った変更は、再読み込みで取得します。リアルタイム同期は未対応です。
- データの取得・保存にはインターネット接続が必要です。
- V1のlocalStorageデータをV2へ自動移行する機能は未実装です。
- メールは受信側の設定などにより、届かない・遅延する場合があります。
- 現在のメール送信構成は少人数での動作確認を中心としており、利用規模の拡大に向けた配信環境の整備は今後の課題です。

## ローカルでの起動方法

Node.js・Gitと、自分のSupabaseプロジェクトを用意してください。
公開ワークフローではNode.js 24を使用しています。

### 1. リポジトリを取得する

```bash
git clone https://github.com/mikiya-web/workout-app.git
cd workout-app
npm ci
```

### 2. SupabaseのDBを準備する

新規のSupabaseプロジェクトで、`supabase/sql`内のSQLを番号順に実行します。

```text
001_create_exercises_and_categories.sql
002_initialize_user_data.sql
003_add_exercises_and_categories.sql
004_update_exercises.sql
005_delete_exercises.sql
006_daily_infos.sql
007_workout_records_and_sets.sql
008_create_workout_record.sql
009_update_workout_record.sql
010_delete_workout_record.sql
```

これらは新規環境の構築用SQLです。
作成済みの環境へ、そのまま繰り返し実行することは想定していません。

### 3. 環境変数を設定する

`.env.example`を参考に、プロジェクト直下に`.env.local`を作成します。

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

URLとキーは、同じSupabaseプロジェクトのものを使用してください。
ブラウザ用のPublishable Keyを設定し、管理者用のSecret Keyやservice_roleキーは使用しないでください。

`.env.local`はGitへコミットしません。

### 4. 認証の設定をする

Supabase Authでメール・パスワード認証とメール確認を設定します。
確認メール・パスワード再設定メールを送信するためのSMTPも設定してください。

ローカル動作確認用のRedirect URLsには、次を登録します。

```text
http://localhost:5173/workout-app/
http://localhost:5173/workout-app/?auth=recovery
```

公開する場合は、自分の公開URLも登録し、Site URLを公開先に合わせて設定します。

### 5. 開発サーバーを起動する

```bash
npm run dev -- --port 5173 --strictPort
```

起動後、次のURLをブラウザで開きます。

```text
http://localhost:5173/workout-app/
```

### コードのチェック

```bash
npm run lint
```

### ビルド

```bash
npm run build
```

Windowsでnpmコマンドを実行できない場合は、`npm`を`npm.cmd`に置き換えてください。

## GitHub Pagesへの公開設定

GitHub Actions Secretsに、次の2つを登録します。

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

Secretの値には、URLまたはキーの値だけを入力します。
変数名・`=`・引用符は含めません。

`main`へのpush時、または`main`を指定した手動実行時に、GitHub Actionsでビルドと公開を行います。

環境変数はビルド時に組み込まれるため、Secretsを変更した場合も再ビルド・再公開が必要です。
